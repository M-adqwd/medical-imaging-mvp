## 一、数据接入与集成

| 需求 | 状态 | 依据 |
|---|---|---|
| 支持 DICOM 3.0，兼容 CT/MRI 导入 | ✅ **已具备** | WADO-RS 取实例；解码器已注册 JPEG / JPEG2000 / JPEG-LS / HTJ2K / RLE，MRI 常用压缩全覆盖。实测 128 实例全部可取回 |
| 支持 PACS 调阅 | ⚠️ **有条件** | `dicomweb` 适配器已写好，配 `DICOMWEB_BASE_URL` 即对接 Orthanc（见 ADR-001）。但当前 `/healthz` 是 `dicomweb_mode: local`，尚未真正对接，也未做 C-FIND/C-MOVE（DIMSE） |
| 光盘、移动存储导入 | 🔧 **能做到** | 已实现 DICOMDIR 解析 + 目录导入端点（含无扩展名 DICOM 文件的 `DICM` magic 识别） |
| 支持 HL7 | ❌ **做不到** | 代码库里 **零处** HL7 相关实现。这不是写个解析器的工作量：HL7 v2 需要消息路由、ADT/ORM/ORU 触发事件、字段映射表，本质是再接一个集成引擎（Mirth / HAPI）。当前没有这个组件 |
| 支持 FHIR（读） | ✅ **已具备**（2026-10-29） | `/fhir/*` 只读门面：Patient / ImagingStudy / DiagnosticReport / Observation / Endpoint，FHIR R4，content-type `application/fhir+json`。与 Case / Study / Report / Measurement 模型对齐，可见性过滤与病例列表同一套。**不含**写侧、订阅、bulk export；测量类型无可靠 LOINC 映射，用本地 code system 如实声明 |
| 与 HIS、EMR、PACS 对接 | ⚠️ **有条件** | PACS 侧有路（DICOMweb）；HIS/EMR 侧完全依赖 HL7/FHIR，因此被上一项阻塞 |
| 预留 AI 接口（RESTful API / SDK），支持三维自动分割、病灶识别接入 | ✅ **已具备** | `POST /ai/infer` 投递 + `POST /ai-results` 回调 + `GET /ai/jobs/{id}` 查询，结果落为 suggested 态等待医师确认。契约完整。**但当前是桩**（见 ADR-002），`ai_mode: stub` |

**小结**：数据接入这条里，**HL7 仍做不到**（需要集成引擎）；FHIR 读取侧已具备（2026-10-29 落地只读门面），写侧待院内接口信息。其余具备或可做到。

## 三、分割编辑与手术规划

| 需求 | 状态 | 依据 |
|---|---|---|
| 自动 / 半自动 / 手动分割工具，器官 / 血管 / 骨骼分离 | ⚠️ **部分具备** | **半自动（种子点区域生长）已通**：`POST /cases/{id}/segments/grow` 在 HU 体数据上做 3D 区域生长，产出**带 PixelData 的 BINARY SEG**（坐标 / 间距 / 方位齐全）。**全自动（2026-10-28 接入）**：`AI_LOCAL_INFER=1` 时 `/ai/infer` 走本地 TotalSegmentator（nnU-Net CPU --fast），多结构逐个回调产出 suggested 态带像素 SEG（ADR-002 修订记录）；权重首跑需下载、CPU 推理以分钟计、对合成体模的识别率未验证。逐层手工勾画（笔刷 / 套索）未做 |
| 裁切 / 平滑 / 布尔编辑 | ⚠️ **部分具备** | **布尔合并已落到像素**：union / intersection / difference 逐体素运算，要求同栅格（跨栅格需重采样，明确 422 拒绝而非静默错位）。源 SEG 无像素时合并直接拒绝——不再产出"名字叫完整肝脏、实际 0 像素"的空壳。裁切、平滑、边缘羽化未做 |
| 三维入路模拟 | ✅ **已具备（本地分割范围内）** | 入路点 / 靶点采集 + 三维视口画轴线已有。现在风险判据改为**入路轴线到分割外表面的最小距离**（表面 = 掩膜 6 邻域腐蚀后的边界层），轴线穿入分割恒判 0 距离；靶点在分割内（即靶区）不参与分级并写明原因 |
| 距离测量 | ✅ **已具备** | `safe_distance`（入靶直线长度）与 `anatomical_distance_mm`（到分割表面最小距离）是**两个独立字段**，后者才是风险分级依据。SEG 无像素 / 无定位时 `anatomical_distance_mm=null`、`risk_level=unknown`，`risk_basis` 写明原因 |
| 角度测量 | ✅ **已具备** | AngleTool 已接线；规划里另有入路轴线夹角计算 |
| 病灶体积计算 | ✅ **已具备（种子生长分割）** | voxel 计数 × 三轴 spacing 乘积，SEG 带像素即可算；界面不可手填（选项禁用 + 说明），无像素时显示「不可用」而非 0 |
| 二三维联动定位 | ✅ **已具备** | 2D 三视口间十字线联动已通；三维视口加入后与 2D 的联动也已实现 |

**小结**：分割这一块从「被同一根因（无像素来源）整体堵死」变成了「**半自动链路已通**」：种子 → 带像素 SEG → 体积 / 解剖距离 / 布尔合并 → 风险分级，端到端有测试与门禁守着。剩余缺口（全自动分割、手工勾画、裁切平滑、跨栅格重采样）是增量功能而非能力性阻塞；REGULATORY 定性（Q-RA-CLASSIFICATION）仍会改变它们的优先级。

## 五、专科模块（骨科 / 肝胆 / 神经，选配一个）

| 需求 | 状态 | 依据 |
|---|---|---|
| 提供专科模块，由医院自行选配 | 🔧 **能做到** | 属配置化而非算法能力，见下 |

专科包的实质是三类配置的组合，都不需要新算法：

1. **窗宽窗位预设** —— 各专科默认值不同（骨窗 / 腹窗 / 脑窗）
2. **结构化报告模板** —— 已有 `template_id` 机制（`ct-chest-default-v3`），按专科换模板
3. **分割标签集** —— 从 TotalSegmentator 的 100+ 结构里取该专科关心的子集

**建议选肝胆**：与现有演示数据（肝脏分割）最贴合，且 `WL_PRESETS` 与报告模板已有基础。骨科需要植入物模板库、神经需要脑区图谱，都不是配置能解决的。

## 三条根因

做到与做不到之间，其实只有 **3 个根因**，把它们拎出来比逐条排期更有用：

| 根因 | 堵死了 | 解除条件 |
|---|---|---|
| ~~R1：没有分割像素来源~~ **R1 已解除（本地半自动路径）** | 曾经堵死：分割、布尔编辑、病灶体积、有临床意义的入路模拟 | 已落地：种子点区域生长直接在 CT 的 HU 体数据上产出带像素 SEG（`app/services/segmentation.py` + `app/dicom/mask.py`）。仍未覆盖的全自动分割需要模型（TotalSegmentator / MONAI），那是"接模型"而非"从零造能力" |
| **R2：缺集成引擎** | HL7、FHIR 写侧、HIS/EMR 对接 | 引入 Mirth / HAPI 之类的集成引擎 + 字段映射表。这是另一个系统，不是本项目的子模块。**注**：FHIR 读取侧不需要集成引擎——本服务自己就是资源生产者，只读门面已于 2026-10-29 落地 |
| **R3：缺配准算法** | 多模态融合 | 引入 ITK / Elastix 做配准，Cornerstone 只负责渲染，不提供配准 |

**剩下的两条（R2 / R3）都不是"多写点代码"能解决的**——它们各自需要引入一个外部能力。把它们误当成排期问题，是最容易犯的规划错误。R1 的解除也印证了另一半教训：真正的缺口（没有像素来源）被识别后，本地路径是"多写点代码"就能解决的——难的是先承认它存在。

另外一条独立项：**多人实时协作**没有开箱即用方案（选型文档自己承认），需要自建 WebSocket 同步层，属纯自研。
