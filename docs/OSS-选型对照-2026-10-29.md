## 摘要

1. **文档的 21 条需求，项目实际覆盖 16 条**（3 条原样落地、7 条等价替代或超出、6 条部分覆盖），**3 条未实现、1 条环境未就绪、1 条有意不做、1 条具备能力未启用**。剩下的硬缺口：DIMSE 接入、HL7 v2、手工勾画（前两条在"接进医院"这一侧，手工勾画卡临床闭环），外加 TotalSegmentator 运行环境这个"演示就会暴露"的配置问题。
2. **文档最大的偏差不是"开源够不够用"，而是低估了业务层。** 它假设开源件能覆盖需求，但开源件只覆盖"看图和分割"；契约里的状态机、幂等、权限矩阵、审计、版本化引用、SR/SEG 合规落库，在 OHIF / Slicer / Orthanc 里一行都没有。
3. **文档的隐含路线是桌面中心（3D Slicer 当主力），项目是 Web 优先。** 这条战略分歧导致 Slicer 那条腿被整条换成自研，于是"简单集成"变成了本项目最重的工作量。文档末尾"2–3 周出原型"只对"能看能画"成立。

## 三、三处方向性偏离（比单条缺口更重要）

### 偏离 1：文档是桌面中心，项目是 Web 优先

文档把 3D Slicer 当作分割、规划、报告、录像的**落地主体**（"SlicerIGT 是专门做这个的"、"3D Slicer 更强"）。项目定位是 Web 优先承载日常阅片、桌面只做复杂规划。结果：Slicer 覆盖的那 5–6 条能力全部要在浏览器里重写一遍，这是 `VrViewport` / `MeshViewport` / 区域生长 / 规划几何的直接来源。

→ **文档的"最低落地成本路线"其实是桌面路线，与 Web 优先的产品定位不兼容。** 选它等于选了另一款产品。

### 偏离 2：开源件不覆盖业务层，文档没算这块

文档结论说"唯一需要二开的是实时协作，其他都能直接集成"。实际二开量最大的恰恰是文档完全没提的部分：状态机转移表、幂等键、五角色权限矩阵、审计、版本化引用校验、SR/SEG 合规生成、错误码分层。130 项后端测试基本都在测这些。

→ 这类工作在任何开源方案里都是 0 行代码可复用，**与选型无关，只与工作量有关**。文档把它算进"直接集成"是最大的估算偏差。

### 偏离 3：Orthanc 被当成 DCM4CHEE 的等价替代

文档 1.2 条推荐 DCM4CHEE-arc-light 做 PACS 调阅，1.4 条推荐 Orthanc 做轻量对接——这是两件事，项目只落了后者。Orthanc 强在 REST/DICOMweb 与插件化，但 **DIMSE 侧（C-FIND/C-MOVE/C-GET 客户端能力）不能替代 DCM4CHEE**。接到院内老 PACS 时这条会立刻暴露。

4. **结论段补业务层工作量**：把"2–3 周出原型"拆成"看图原型 2–3 周 / 可进流程的 MVP 需再加一个与前端渲染同量级的后端"，并点明状态机+权限+合规持久化在开源件中为零。→ 结论段已重写，含六项业务层能力逐条对照"开源件里有没有现成实现"。
