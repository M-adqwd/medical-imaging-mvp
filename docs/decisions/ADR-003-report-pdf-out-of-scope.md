# ADR-003 · 报告导出只出 DICOM SR，PDF 不进首期

- **状态**：已接受
- **日期**：2026-10-27
- **关闭**：PM 提出的「PDF 是否进 MVP」；影响 TC-03 实现路线与选型结论第 46 行表述

## 背景

三处口径互相打架：

1. 开源选型结论第 46 行写「PDF / DICOM 报告生成 | OHIF dicom-pdf 扩展 / 3D Slicer 报告模块 | ✅」。
2. `docs/SPEC.md:41` 已把「Plan 导出 PDF / 导航系统格式」列入「明确不做」表，
   原因栏写的是 PRD FR-05 标记 `[TBD]`。
3. 代码里 `server/app/api/v1/routers/plans.py:115-136` 接受 `format=dicom_sr|pdf`，
   对 `pdf` 返回 501（早期版本返回声明 `application/pdf` 的纯文本，已修）。

需要一次裁决把三处收敛成一个口径。

## 决策

**首期报告/规划导出只产出 DICOM SR。PDF 不进首期。**

## 理由

1. **契约 §0.1 单一事实源**。系统生成的测量与报告必须是 PACS 可读回的标准 DICOM SR。
   PDF 是同一份数据的第二个人类可读渲染 —— 两份真相必然漂移，而"哪份算准的"
   在临床场景里是个不能靠约定解决的问题。首期不为它付这个维护成本。
2. **依赖与部署成本**。`server/requirements.txt` 里没有任何 PDF 库。
   中文报告用 reportlab 或 weasyprint 都需要嵌入 CJK 字体，通常是一个 10MB 量级的
   字库文件进入镜像 —— 这是部署形态的变化，不是加一行依赖。
3. **需求可以被更便宜的方式满足**。打印与分享走浏览器：web 报告页 + print stylesheet，
   用户 Ctrl+P 即可得到 PDF。这条路不需要服务端产物，也不引入第二份事实源。
4. **范围 Gate 已经是这个结论**。SPEC §3 与 PRD FR-05 双双指向"不做 / 待定"，
   裁决只是把代码和文档对齐到已有结论。

## 强制约束（否则此项决策会退化为静默失效）

- **绝不允许"声明 `application/pdf` 但返回非 PDF 内容"。**
  这与 addTool 未注册是同一类静默错误：客户端按 PDF 处理会在远离原因的地方失败，
  而服务端看起来一切正常。当前 `plans.py:129-136` 返回 501 是正确的止血，保留。

- **终态是移除 `format` 查询参数。**
  首期只有一个合法导出格式，参数本身只应在存在多个取值时才存在。
  保留一个永远 501 的取值，等于在 API 上留一个假入口 ——
  调用方会读成"功能存在，只是暂时不可用"，进而为它排期、等待。
  删掉之后调用方连试都不会试，这才是诚实的接口。
  后续若真要支持 PDF，走新 endpoint 或 `/api/v2`，不是给旧参数加取值。

- **若因兼容考量必须保留参数**，最低要求是：`/contract` 与 OpenAPI 中 `format`
  的 enum 只有 `dicom_sr`；对 `pdf` 的错误消息必须写清
  "首期不支持 PDF 导出，请使用 DICOM SR；打印请使用浏览器打印"。
  不允许出现只说"不支持"却不给替代路径的提示。

## 后果

- **选型结论第 46 行必须拆分改写**，不能继续用一个 ✅ 盖住两件事：
  - DICOM SR 报告生成：**已实现**（`server/app/dicom/sr.py` 产出 Comprehensive SR，
    实测返回 `application/dicom`，字节流偏移 128 处为 `DICM`）
  - PDF 报告生成：**有意不做**（不是"未实现"）—— 且 OHIF dicom-pdf 从未被依赖，
    OHIF 在项目里只出现在一处 CSS 注释中。这一格现在是双重失真：
    既谎报了 PDF，也谎报了 OHIF dicom-pdf 的采用状态。
- 报告打印需求落到前端 print stylesheet，不在服务端生成文件。
- 后续若要纳入 PDF，必须新开 ADR，并同时解决"PDF 与 SR 内容一致性"的
  自动化校验 —— 同一份数据渲染，禁止手工维护两套模板。
